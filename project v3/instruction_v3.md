# DSCAD Dilithium 부채널 공격 v3 설계 사양

v2의 한계를 실측으로 진단하고, 정규화 / 학습 / 평가 세 축을 재설계한다.
이 문서의 모든 수치는 원본 데이터셋 헤더, 공식 `Verification.ipynb`, 그리고
`attack_10000_u=cs.npy` / `attack_10000_c.npy` / `attack_s.npy` 실측에서 나왔다.

## 0. 확정된 데이터셋 사실

| 파일 | shape | dtype | 크기 |
|---|---|---|---|
| `profiling_40000traces_set1~4.npy` | (10000, 40000) | int64 | 각 3.05 GB |
| `profiling_40000_u=cs.npy` | (40000, 4, 256) | int32 | 156 MB |
| `attack_10000traces.npy` | (10000, 40000) | int64 | 3.05 GB |
| `attack_10000_u=cs.npy` | (10000, 4, 256) | int32 | 39 MB |
| `attack_10000_c.npy` | (10000, 256) | int32 | 9.8 MB |
| `attack_s.npy` | (4, 256) | int64 | 8.3 KB |
| `rho.npy` | (20, 40000) | float64 | 6.4 MB |

전체 15.3 GB. 공식 검증 노트북이 정의하는 관계는 다음과 같고, 직접 재검증했다.

```
u[i][j][k] = MR(c[i][k] * s[j][k])      # NTT 도메인 계수별 pointwise 곱
```

### 정정 사항

- **v1/v2 `instruction.md`의 "총 160,000개 트레이스"는 오류다.** 각 set이 10,000개이므로
  프로파일링 전체는 10,000 x 4 = **40,000개**다. v2 전처리가 4개 set을 `vstack`해 만든
  40,000행은 라벨 `(40000, 4, 256)`과 정확히 일치하며, 이 부분에 버그는 없다.
- **v2 `report.md`의 "시맨틱 피크 250개"는 실제로 4개다.** 저장된 `poi_indices.npy`는
  60개(= 4 x 15)이고 `X_train_poi400.npy`는 `(40000, 60)`이다.
  `find_peaks(height=0.03, distance=30)`가 4개만 반환했는데
  `peaks[np.argsort(...)[-250:]]`가 개수 부족을 조용히 통과시켰다.
- **v2 `report.md`의 "Log-Prior Correction"은 코드에 존재하지 않는다.**

### rho.npy 구조 (해독됨)

20개 행 = **4 polynomial x 5 coefficient**. 피크 위치는 다음과 같다.

```
poly0: 1828  3578  5328  7078  8828     (간격 1750)
poly1: 11831 13388 14888 16388 17888    (간격 1500)
poly2: 21578 23078 24578 26078 27578    (간격 1500)
poly3: 31578 33078 34578 36078 37578    (간격 1500)
```

다항식 구간은 정확히 10,000 샘플(= 40000/4) 간격이고, 계수 1개당 약 30~35 샘플이다.
즉 **트레이스 1개(40,000 샘플) 안에 1024개 계수 연산이 순차적으로 모두 들어있다.**
누설은 매우 강하고 국소적이다(`max|rho| = 0.7249`, 원거리 2위 피크는 0.022).

`v3_common.calibrate_time_map()`으로 실측 보정한 뒤 사용할 것. 기본 파라미터는
poly0 기준이라 poly1~3에서 어긋난다.

## 1. 라벨 분포와 올바른 베이스라인

`hw32(u[:, 0, 50])`은 **이봉분포**다. `& 0xFFFFFFFF` 때문에 음수 u는 HW 20~22,
양수는 HW 11~12에 몰린다 (음수 5035 / 양수 4965).

```
무작위 (1/33)                =  3.03%
다수 클래스(HW=11) 항상 예측 =  8.68%   <- 실제 베이스라인
v2 보고 Top-1                = 54.35%
```

따라서 **v2의 54%는 진짜 신호다.** 다수 클래스 대비 6.3배로, 클래스 불균형
아티팩트가 아니다. 다만 `max|rho| = 0.72`짜리 누설에서 54%면 오히려 낮은 편이며,
전처리에서 성능을 남기고 있다는 근거다.

모든 정확도 보고는 반드시 8.68%와 함께 제시한다.

## 2. 정규화 재설계 (`v3_normalize.py`)

정규화 순서: `box filter -> per-trace gain -> POI 슬라이스 -> vertical z-score`

### 2.1 per-trace 이득 보정을 추가한다

v2 `instruction.md`은 "개별 트레이스 정규화 금지"를 못박았지만 이는 **POI 구간에서**
트레이스별 정규화를 할 때만 맞는 말이다. 트레이스 전체 40,000 샘플에서 robust
scale(median/MAD)을 재면 데이터 의존 성분이 전체 분산의 극히 일부이므로 신호를
지우지 않으면서 측정 이득과 DC 드리프트만 제거된다.

합성 캠페인(DC +120 드리프트 주입) 검증 결과:

| 설정 | 누설 rho | 캠페인 평균 이동 |
|---|---|---|
| v2 방식 (gain 보정 없음, 통계 이식) | 0.8155 | **8.02 sigma** |
| + per-trace gain 보정 | **0.9356** | 0.006 sigma |
| + 캠페인 자체 통계 | 0.9356 | 0.000 sigma |

이득 보정 하나로 누설 상관계수가 오르고 도메인 격차가 사라진다.
(합성 데이터 기준이므로 실제 트레이스에서 재측정할 것.)

### 2.2 vertical 통계량을 캠페인 자체에서 뽑는다

v2는 프로파일링 통계량을 공격셋에 이식해 캠페인 간 격차를 그대로 안고 갔다
(val 58.9% vs 공격 54.35%의 4.5pt 갭). 공격자는 공격 트레이스 10,000개를
보유하므로 **그 평균/표준편차를 계산하는 것은 라벨을 전혀 쓰지 않는 정당한
비지도 도메인 적응**이다. `vertical_source="own"`이 기본값이며,
`"external"`로 두면 v2 동작을 그대로 재현해 A/B 비교할 수 있다.

`portability_report()`로 격차를 항상 정량화한 뒤 결정한다.

### 2.3 통계량은 전체 트레이스로 계산한다

v2는 `std_dpt`를 set1의 앞 5,000개로만 추정했다. 4개 set이 서로 다른 측정
세션이면 set2~4의 노이즈 스케일이 반영되지 않는다. 또 저장된 `global_std.npy`는
전처리 노트북이 계산조차 하지 않는 다른 실행의 잔재다.

### 2.4 필터 경계 처리

v2의 `np.convolve(mode='same')`는 양 끝을 0으로 패딩해 경계를 왜곡한다.
`box_filter()`는 edge 패딩 + 누적합이라 경계가 안전하고 훨씬 빠르다.
MA 윈도우 5는 인접 샘플을 상관시켜 15샘플 윈도우의 실질 독립 정보를 ~3개로
줄이므로, `moving_average=1`(필터 없음)과 반드시 A/B 한다.

### 2.5 POI 선택

`rho` 기반 선택은 누설이 HW에 선형이라는 가정에 묶인다. `snr()`로 대체하고,
`select_poi()`는 **개수를 보장**하며 확보 실패 시 예외를 던진다 — v2의 조용한
실패가 구조적으로 재발할 수 없게 한다.

## 3. 학습 재설계

### 3.1 손실 함수: 이중 보정 제거

v2는 `CategoricalFocalCrossentropy`와 `class_weight='balanced'`를 **동시에** 적용했다.
focal loss가 이미 다수 클래스를 억제하는데 balanced weight를 또 곱하면 희소
클래스가 이중 증폭되어 softmax 출력이 사후확률에서 크게 벗어난다.
**SCA에서는 치명적이다** — 공격이 로그확률 누적이라 캘리브레이션된 확률을 전제한다.
v2가 `temperature=5.0`으로 분포를 강제 평탄화해야 했던 것이 이 왜곡의 증상이다.

또한 다중 클래스 focal loss의 `alpha=0.25`는 모든 클래스에 동일하게 곱해지므로
사실상 학습률만 0.25배로 줄이는 효과다.

v3: **class_weight 제거**, 표준 CE + label smoothing을 기본으로 하고
캘리브레이션은 학습 후 별도 검증셋에서 온도로 처리한다.

### 3.2 Val Acc > Train Acc 해석 정정

v2 `report.md`는 이를 "물리적 본질을 학습한 증거"로 해석했으나,
`Dropout(0.6)`이 걸린 상태에서 train accuracy는 규제가 켜진 채, validation은
추론 모드로 측정되므로 **강한 드롭아웃이면 항상 나타나는 아티팩트**다.
일반화의 증거가 아니다.

`GaussianNoise(0.05)`도 이미 단위분산인 데이터에 sigma=0.05를 더하는 것이라
증강 효과가 거의 없다. 실질적인 증강은 **랜덤 시간 이동(+-몇 샘플)** 이다.

### 3.3 아키텍처: 윈도우 경계 문제

v2 입력 60샘플은 물리적으로 떨어진 **4개 윈도우를 이어붙인 것**인데 모델은 이를
하나의 연속 시계열로 보고 kernel=11 컨볼루션을 건다. 15샘플마다 있는 인위적
경계를 커널이 가로질러 무관한 시간 구간을 섞고, MaxPooling 3회로 60->7이 된 뒤
GAP으로 윈도우 구분이 완전히 사라진다.

v3: 입력을 `(윈도우 수, 윈도우 길이)`로 재구성해 **윈도우별 독립 브랜치 -> 후단 결합**.

### 3.4 데이터를 1024배 더 쓴다 (v3의 핵심)

트레이스 1개가 1024개 계수 연산을 모두 담고 있고 라벨도 `u[i, j, k]`로 1024개가
전부 있는데, **v2는 `[:, 0, 50]` 하나만 썼다.**

계수 k의 누설이 시간축에서 `~10000*j + 33*k` 부근에 선형 배치되므로, 윈도우를
옮겨가며 학습하면:

- 학습 샘플: 40,000 -> 최대 **약 4천만 개**
- 계수 불변(shift-invariant) 모델 1개로 **1024계수 전체 복구가 자동 해결**
- 계수마다 POI를 다시 뽑을 필요가 없어짐

즉 Stage 2(전처리·학습)와 Stage 3(전체 키)이 별개 작업이 아니라 하나의 설계로 합쳐진다.

### 3.5 검증 분할

랜덤 분할은 같은 캠페인 내부라 낙관적이다. **leave-one-set-out**(set1~3 학습 /
set4 검증)으로 캠페인 이동 성능을 정직하게 측정한다.

## 4. 평가 재설계 (`v3_evaluate.py`)

### 4.1 v2 평가가 무효인 이유

```python
# project v2/project_v2_attack_evaluation.ipynb
s_candidates = np.unique(s_atk_all[0])   # <- 정답 비밀키 파일
```

후보군을 **정답 키에서 생성**했다. 실측 결과 `attack_s.npy`의 poly0는 256개 값이
전부 서로 다르므로 후보는 256개이고, 실제 탐색공간 q = 8,380,417 대비
**32,736배 축소**다. 정답이 반드시 포함된 채로 GE를 잰 것이라 GE=0은 공격 성공의
증거가 되지 못한다. `temperature=5.0`을 공격셋에서 직접 고른 것도 테스트셋 튜닝이다.

### 4.2 정직한 후보 공간

`MR(c*(s+q)) == MR(c*s)`가 성립하므로(수학적으로 `q*qinv = 1 mod 2^32`에서 유도되고
실측 확인함) 후보 공간은 **q개 잔여류**다. 대표원은 `(-q/2, q/2]`을 쓴다 —
`[0,q)` 대비 불일치가 적다(0.058% vs 0.080%, 차이는 정확히 +-q인 int32 오버플로
경계 사례).

`build_candidate_residues()`는 시드 고정 균등추출로 후보를 만들며 **정답 키 파일을
후보 생성에 절대 쓰지 않는다.** 정답은 순위 계산 대상 지정과 부분집합 포함 보장
용도로만 삽입되고, 부분집합 순위는 `scale_to_full_space()`로 q 공간 순위로 환산한다.

### 4.3 동점 처리 (필수)

HW는 33개 값뿐이라 서로 다른 s 후보가 **동일한 HW 시퀀스를 내는 일이 흔하다.**
단순히 `(score > true_score)` 개수만 세면 동점 후보가 전부 무시되어 GE가 0으로
붕괴한다 — 아직 구분되지 않았는데 복구에 성공한 것처럼 보이는 심각한 과대평가다.

실제로 완벽 오라클을 동점 처리 없이 재면 N=1에서 GE=0이 나온다(잘못됨).
평균 순위(mid-rank)를 쓰면 N=1에서 GE=2116으로 정상화된다.

### 4.4 캘리브레이션 분리

온도와 사전확률 보정은 **공격셋과 분리된 캘리브레이션셋**에서만 학습한다
(`fit_temperature`, `implicit_log_prior`). `implicit_log_prior`는 모델이 실제로
가진 사전확률을 예측 평균에서 추정해 빼며, 이것이 v2 `report.md`가 주장했지만
구현하지 않은 보정이다.

### 4.5 완벽 오라클 기준선

HW를 100% 맞히는 오라클의 GE 곡선을 항상 함께 보고한다. 실측값:

```
N=1: GE=2116.4  SR=  0.0%
N=2: GE= 132.0  SR=  0.0%
N=3: GE=   7.9  SR=  0.0%
N=4: GE=   0.33 SR= 55.0%
N=5: GE=   0.01 SR= 97.5%
N=6: GE=   0.00 SR=100.0%
```

**어떤 모델도 6개 트레이스보다 적게 복구할 수 없다.** 트레이스 1개가 주는 정보는
약 4비트이고 q 공간은 23비트다.

### 4.6 예상 결과

정확도를 제어한 합성 모델로 정직한 프로토콜을 돌린 결과(후보 65,536개, 실험 40회):

| 모델 Top-1 | 학습된 T | SR 100% 도달 N |
|---|---|---|
| 64.6% | 0.40 | 8 |
| 47.4% | 0.40 | 8 |
| 31.7% | 0.40 | 13 |
| 21.4% | 0.40 | 13 |

주목할 점 두 가지.

1. **v2의 "50개 트레이스"는 과소평가였다.** 정직한 후보 공간에서도 54% 수준
   모델이면 10개 미만으로 충분해야 한다.
2. **v2의 `T=5.0`은 방향이 반대였다.** 캘리브레이션으로 학습된 온도는 0.4로
   분포를 *날카롭게* 만든다. v2는 평탄화해서 정보를 버리고 있었다.

(합성 모델 기준이므로 실제 모델로 재확인할 것.)

## 5. 단계별 로드맵

| 단계 | 내용 | 산출물 | 트레이스 필요 |
|---|---|---|---|
| Stage 0 | 데이터 검증 게이트 | `v3_common.verify_dataset()` | 헤더만 |
| Stage 1 | 평가 신뢰성 복구 | `v3_evaluate.py` | 공격셋 |
| Stage 2 | 정규화 / POI / 학습 재구축 | `v3_normalize.py` + 모델 | 전체 |
| Stage 3 | 1024계수 확장 | 계수 불변 모델 | 전체 |

Stage 1을 지나면 **GE 수치가 v2 보고치보다 나빠 보일 수 있다.** 그것이 정상이며,
그 수치가 Stage 2/3의 개선 폭을 재는 유일한 기준선이다.

## 6. 트레이스 확보 후 최우선 확인 항목

1. `verify_dataset()` 통과 — shape/dtype/MR 관계/HW 분포
2. `calibrate_time_map()`으로 poly0~3 각각의 `(coeff_stride, offset)` 실측
3. 4개 set 간 평균 트레이스 비교 — set별 캠페인 드리프트 존재 여부
4. `portability_report()`로 프로파일링 -> 공격 격차 정량화
5. `moving_average` 1 vs 5, `vertical_source` own vs external A/B
6. rho[0]이 정말 coeff 50인지 확인 (v2가 54%를 얻은 사실로 미루어 맞지만 명시 검증)

## 7. Stage 2 구현 (`v3_stage2_data.py`, `v3_model.py`)

### 7.1 계수 불변 파이프라인

`build_normalized_memmap()`이 원본 int64 트레이스를 **정규화된 float16 memmap**으로
1회 변환한다(12.2 GB -> 3.2 GB). 2패스 구조로, 1패스는 시간샘플별 통계를 Welford로
누적하고 2패스는 정규화 결과를 디스크에 쓴다. 원본을 메모리에 올리지 않는다.

`CoefficientWindowSampler`가 트레이스 전 구간에서 `(윈도우, HW)` 배치를 만든다.
`build_time_map()`으로 계수 -> 시간 매핑을 주입하며, 이 값은 반드시
`v3_common.calibrate_time_map()` 실측 결과를 써야 한다.

에폭당 샘플 수: **30,000 -> 30,720,000 (1024배)**.

합성 데이터 검증 결과, 서로 다른 다항식/계수에서 뽑은 윈도우가 하나의 정렬된
표현으로 모인다(윈도우 중심 vs HW 상관계수 **0.9123**). 계수 불변 학습이
성립한다는 근거다.

### 7.2 증강은 랜덤 시간 이동으로

샘플러의 `shift_aug`가 윈도우 중심을 +-n 샘플 흔든다. 이미 단위분산인 데이터에
`GaussianNoise(0.05)`를 더하던 v2 방식과 달리 물리적으로 의미 있는 증강이며,
정렬 오차에 대한 강건성을 직접 학습시킨다.

### 7.3 경계 조건은 예외로 막는다

`build_time_map()`은 매핑이 트레이스 범위를 벗어나면, `CoefficientWindowSampler`는
`window/2 + shift_aug`가 경계를 넘으면 즉시 예외를 던진다. v2의 조용한 실패가
재발할 수 없는 구조다.

### 7.4 Stage 1과의 연결

`predict_coefficient_probs()`가 `(n_traces, 33)` 확률 행렬을 만들어
`v3_evaluate.fit_temperature` -> `trace_log_likelihood` -> `guessing_entropy`로
그대로 넘긴다. 학습과 정직한 평가가 하나의 루프로 닫힌다.

## 8. Apple Silicon 최적화 (`v3_backend.py`)

설치: `pip install tensorflow-macos tensorflow-metal`

### 8.1 통합 메모리에 맞춘 데이터 경로

M시리즈는 CPU/GPU가 RAM을 공유하므로 host->device 복사 비용이 없다. 대신 총량을
공유하므로 사본을 늘리면 그대로 손해다. **float16 memmap + tf.data** 조합이 이
구조에 가장 잘 맞으며, OS 페이지 캐시가 사실상 GPU 캐시 역할을 한다.

### 8.2 배치 지역성 (가장 큰 성능 요인)

무작위 `(trace, 계수)` 쌍을 흩뿌려 배치를 만들면 3.2 GB memmap 랜덤 접근이 되어
페이지 폴트가 폭증한다. 샘플러는 대신 **적은 수의 트레이스만 읽고 그 안에서 계수를
많이 뽑는다**(`traces_per_batch`). 트레이스 행 하나가 80 KB 연속 읽기라 지역성이
크게 좋아진다. 또 제너레이터가 샘플이 아니라 **배치 단위**로 yield 해서 Python
오버헤드가 샘플당이 아니라 배치당으로 줄어든다.

### 8.3 P코어 / E코어

M시리즈는 성능 코어와 효율 코어가 섞여 있다. intra-op 스레드를 논리코어 전체로
잡으면 작업이 E코어로 밀려 오히려 느려진다. `performance_core_count()`가
`sysctl hw.perflevel0.logicalcpu`로 P코어 수를 읽어 맞춘다. numpy(Accelerate)는
`configure_numpy_threads()`로 제한하며, **numpy import 전에** 호출해야 한다.

### 8.4 Metal 백엔드 주의사항

| 항목 | 지침 |
|---|---|
| XLA (`jit_compile=True`) | Metal에서 미지원. `compile_kwargs()`가 항상 끈다 |
| `mixed_float16` | 버전에 따라 불안정했다. 기본 off, 수치 확인 후에만 on |
| Optimizer | TF 2.11+ 신규 Adam보다 `legacy.Adam`이 빠른 사례가 있어 우선 시도 |
| Conv1D | `metal_safe=True`면 `(k,1)` Conv2D 경로 사용 |
| float64 | MPS/Metal에서 취약. 파이프라인 전 구간 float32 유지 |

`build_model(metal_safe=True)`가 기본값이다. Conv1D가 잘 도는 환경이면
`metal_safe=False`로 두는 편이 그래프가 단순하다.

### 8.5 원본 dtype

트레이스가 int64로 저장되어 있어 set 하나가 3.05 GB다. ADC 데이터에 int64는
4배 낭비이므로 **로드 즉시 float32로 캐스팅**하고, memmap에는 float16으로 쓴다.

## 9. 실제 트레이스 검증 결과

전체 15.3 GB는 실측 대역폭 약 0.18 MB/s로 24시간이 걸려 받을 수 없다. 대신
`.npy`가 행 우선 저장이라는 점을 이용해 **HTTP Range로 앞부분 600행만** 잘라 받았다
(`attack_10000traces.npy` 바이트 128 ~ 192,000,127, 8개 병렬 청크로 183 MB).
행 i의 시작 바이트는 `128 + i * 320000`이다.

### 9.1 파이프라인 정합성 확인

- 조립된 트레이스: `(600, 40000) int64`, 값 범위 -17,982 ~ 18,775
- **트레이스당 고유값이 109개뿐**이다. ADC 양자화가 매우 성기므로 int64 저장은
  4배가 아니라 사실상 8배 낭비이고, float16 변환도 정보 손실이 없다.
- poly0/coeff50 상관 피크가 **샘플 1828, |rho| = 0.7044** — `rho.npy` 예측과 정확히 일치.

### 9.2 시간 매핑 실측 (`time_map.json`)

선형 적합은 **poly1에서 최대 145샘플 어긋난다.** 다항식별 계수 간격이 일정하지 않다.

| | 계수 간격 | 선형 잔차 |
|---|---|---|
| poly0 | 약 35 (32~37 변동) | 1.1 샘플 |
| poly1 | 앞부분 35 -> 뒷부분 30 | **145.7 샘플** |
| poly2 | 약 30 (27~32 변동) | 1.4 샘플 |
| poly3 | 약 30 (27~32 변동) | 1.2 샘플 |

따라서 `calibrate_time_map_dense()`로 **1024개 위치를 전부 실측**해 테이블로 쓴다.
결과는 `time_map.json`에 저장되어 있고 `build_time_map()`이 그대로 받는다.

측정 품질: **|rho| 중앙값 0.6686, 최소 0.5198, 0.3 미만 0개.**
1024개 계수 전부가 강하게 누설한다.

### 9.3 이동평균: 이전 권고 정정

실제 데이터로 스윕한 결과다(1024계수 중 64개 표본, |rho| 평균).

```
MA=1  0.6653    MA=3  0.7312    MA=5  0.7434
MA=7  0.7589 (최적)   MA=9  0.7442   MA=11 0.7192   MA=15 0.6650
```

**"필터를 빼고 A/B 하라"던 이 문서의 초기 권고는 실제 데이터에서 틀렸다.**
필터는 확실히 도움이 되며 7 부근이 정점이다. v2의 5는 근접했지만 최적은 아니었다.
`NormConfig.moving_average` 기본값을 7로 바꿨다.

### 9.4 per-trace 이득 보정: 범위 정정

앞서 2.1절에 적은 "0.8155 -> 0.9356" 개선은 **이득 편차를 인위적으로 주입한 합성
데이터 기준**이다. 실제 공격 트레이스에서 캠페인 *내부* 효과는 거의 없다
(0.7427 -> 0.7434). 실제 트레이스에는 트레이스별 이득 편차가 크지 않다.

이 단계의 가치는 캠페인 *간* 이식성에 있으며, **프로파일링 트레이스를 확보하기
전에는 검증되지 않았다.** 해롭지 않으므로 기본 활성으로 두되, 근거는 아직 없다.

### 9.5 계수 불변성 성립 (핵심)

- **누설 극성이 128개 표본 전부 음수로 일관**된다. 모든 계수가 같은 방향으로 누설한다.
- 1024계수를 섞은 윈도우의 |rho| = **0.7399**, 단일 계수 |rho| = **0.7434**.
  **섞어도 손실이 거의 없다.** 가중치 하나가 1024계수 전부를 담당할 수 있다는
  직접적인 실측 근거다.

`shift_aug` 트레이드오프 (window=32, MA=5 기준):

```
shift_aug=0  0.7399     shift_aug=1  0.7236
shift_aug=3  0.6647     shift_aug=5  0.5656
```

시간 매핑을 계수별로 실측했으므로 정렬이 이미 정확하다. 큰 증강은 순손실이며
**1~2를 권장**한다.

### 9.6 캠페인 간 이식성 측정 (완료)

프로파일링 set1의 앞 600행(183 MB)과 해당 라벨 600행(2.4 MB, 행당 4 KB뿐이라 저렴)을
같은 Range 방식으로 확보해 측정했다.

**시간 매핑이 캠페인 간 그대로 전이된다.**

```
프로파일링 피크 - 공격셋 매핑 위치 차이: 중앙값 0.0, 평균절대 0.7, 최대 4 샘플
누설 강도 |rho|: 프로파일링 0.6685 / 공격셋 0.6659
```

`time_map.json`은 공격셋에서 측정했지만 프로파일링에도 그대로 쓸 수 있다.
캠페인마다 재보정할 필요가 없다.

**두 캠페인의 통계 격차가 매우 작다.**

```
평균 이동(프로파일링 sigma 단위): 중앙값 0.0441, p95 0.1234
분산 비율: 중앙값 1.0010, p95 1.0644
```

**전이 성능**: 계수 1024개를 풀링해(각 614,400 샘플) 프로파일링에서만 선형 모델을
학습하고 공격셋에 적용했다.

| 정규화 방식 | 프로파일링 | 공격셋 | 전이 손실 |
|---|---|---|---|
| v2 방식 (프로파일링 통계 이식) | 0.7490 | 0.7385 | 0.0106 |
| v3 방식 (캠페인 자체 통계) | 0.7490 | 0.7386 | 0.0105 |

| per-trace 이득 보정 | 프로파일링 | 공격셋 |
|---|---|---|
| OFF | 0.7486 | 0.7376 |
| ON | 0.7490 | 0.7385 |

### 9.7 정규화 개선안에 대한 최종 정정

**2.1절과 2.2절에 적은 두 개선안은 이 데이터셋에서 효과가 없다.**

- `vertical_source="own"` vs `"external"`: 0.7386 vs 0.7385. 차이 0.0001, 잡음 수준.
- `per_trace_gain`: 0.7385 vs 0.7376. 차이 0.0009.

이유는 명확하다. DSCAD의 프로파일링과 공격 캠페인이 **매우 잘 정합되어 있어
보정할 편차가 애초에 없다**(평균 이동 중앙값 0.044 sigma, 분산비 1.001).
전이 손실 자체가 1.4%에 불과하다.

두 옵션은 비용이 거의 없고 해롭지 않으므로 기본값으로 유지하되,
**이 데이터셋에서 성능 개선을 기대해서는 안 된다.** 측정 세션이 실제로
어긋난 데이터셋을 위한 안전장치로 본다.

정규화에서 실제로 의미 있었던 개선은 **이동평균 폭 7**(0.6653 -> 0.7589) 하나다.

v3의 진짜 기여는 정규화가 아니라 다음 세 가지다.
1. 데이터를 1024배 활용 (계수 불변 학습)
2. 평가의 정직성 회복 (후보 공간, 동점 처리, 캘리브레이션 분리)
3. 시간 매핑 실측 (선형 가정 폐기)

### 9.8 아직 검증하지 못한 것

- TensorFlow/Metal 코드는 이 환경(x86 리눅스, TF 미설치)에서 **실행 검증 불가**.
  구문 검사만 통과했다.
- 실제 모델 학습 및 그에 따른 정직한 GE/SR 측정.
  (프로파일링 트레이스 600행만 있어 본격 학습은 불가)

## 10. 학습 정확도 개선 (실측 기반)

"더 나은 학습 알고리즘"을 일반론이 아니라 실측으로 찾았다. 실제 트레이스
600+600개로 네 가지 실험을 돌렸다.

### 10.1 딥러닝이 정말 필요한가 — 그렇다

계수 1024개를 풀링해 LDA(선형 판별분석) 템플릿을 만들었다. 고전 프로파일링
공격의 대표적 상한이다.

```
LDA 템플릿   프로파일링 17.80%  ->  공격셋 17.57%   (베이스라인의 2.09배)
v2 CNN                              54.35%          (베이스라인의 6.26배)
```

**CNN이 LDA의 3배다.** 누설이 선형적으로 보여도(|rho|=0.75) 깊은 모델이
확실한 이득을 준다. 딥러닝 유지가 옳다.

### 10.2 계수 하나가 여러 지점에서 누설한다 (윈도우를 넓혀라)

누설이 단일 지점이라고 가정했는데 틀렸다. 피크 주변 ±200 샘플을 훑어보니
**계수 하나당 봉우리가 6~7개**다.

```
poly0/coeff50  상대위치: -1(0.807)  +15(0.650)  +24(0.662)
                          +36(0.311) +55(0.251)  +64(0.202)
poly2/coeff128 상대위치:  0(0.787)  +17(0.605)  +26(0.627)
                          +37(0.472) +54(0.326)  +65(0.197) +101(0.155)
```

`window=32`(-16~+16)는 앞의 두 개만 담고 **+24 이후를 통째로 버린다.**
+24 지점의 |rho|가 0.662로 주 피크 다음으로 강한데도 그렇다.

윈도우를 넓히고 뒤로 밀어서 실측한 결과(윈도우 전체 선형결합의 |rho|):

| window | offset | \|rho\| | 개선 |
|---|---|---|---|
| 32 | 0 | 0.7974 | 기준 |
| 48 | 8 | 0.8536 | +7.0% |
| 64 | 16 | 0.8587 | +7.7% |
| 96 | 24 | 0.8748 | +9.7% |
| 128 | 32 | 0.8966 | +12.4% |
| 160 | 40 | 0.9067 | +13.7% |

**window=96~128, window_offset=24~32을 권장**한다. 128 이후는 수확체감이고
이웃 계수와의 중첩이 커진다. `CoefficientWindowSampler(window_offset=...)`로 지원한다.

### 10.3 라벨을 바꾸면 정보량이 2.1배 (가장 큰 지렛대)

HW(u) 하나를 예측하는 것은 정보량 상한이 낮다. 비트별로 누설 강도를 재봤다.

```
byte0 (bit 0~7)   |rho| 0.2446        bit 0  0.1532   bit 8  0.1844
byte1 (bit 8~15)  |rho| 0.2955        bit16  0.1322   bit20  0.1325
byte2 (bit16~23)  |rho| 0.5748        bit24  0.7238   bit28  0.7238
byte3 (bit24~31)  |rho| 0.7238        bit31  0.7238
전체 HW           |rho| 0.8072
```

**bit24 / bit28 / bit31의 |rho|가 0.7238로 완전히 같다.** `|u| < 2^23`이라
상위 9비트가 전부 부호 확장이기 때문이다. 즉 **HW(u)의 절반가량은 사실 부호 1비트**다.
byte3의 HW는 사실상 `8 x 부호비트`다.

라벨을 분해하면 정보량이 크게 는다.

공격셋 u 전량(10,240,000 샘플)으로 엔트로피를 실측했다.

| 라벨 | 엔트로피 | HW 대비 | 필요 트레이스 |
|---|---|---|---|
| sign (1비트) | 1.0000 | 0.237배 | 23.0 |
| **HW 전체 (33클래스)** | **4.2147** | 1.000배 | **5.46** |
| 멀티태스크 주변 합 (상한, 쓰면 안 됨) | 8.7853 | 2.084배 | 2.62 |
| **멀티태스크 결합 (실제)** | **8.4157** | **1.997배** | **2.73** |

**주변 엔트로피의 단순 합을 쓰면 안 된다.** 헤드가 완전히 독립일 때만 성립하는
상한이고, 실제로는 0.3696비트(4.2%)가 중복이다. 결합 엔트로피를 써야 하며,
그러면 배율이 2.084가 아니라 **1.997배**다.

`byte3`은 헤드에 추가해도 결합 엔트로피가 **+0.0000비트**다. `sign`과 완전히
중복이므로 기본 헤드 조합에서 제외한다.

**멀티태스크 학습을 권장한다.** 공유 트렁크에 헤드를 여러 개 달아
sign / byte0 / byte1 / byte2를 동시에 예측하고, 공격 시 로그우도를 합산한다.
`v3_model.build_multitask_model()`, `v3_stage2_data.precompute_multitask_labels()`.

**다만 상한과 실현치는 다르다.** 헤드마다 학습 난이도가 크게 다르다.
선형 프로브(온도 보정 후) 실측이다.

| 헤드 | 누설 \|rho\| | H(Y_h) | 실측 PI_h | Top-1 |
|---|---|---|---|---|
| sign | 0.72 | 1.000 | **+0.643** | 91.21% |
| byte2 | 0.57 | 2.692 | +0.096 | 31.47% |
| byte1 | 0.29 | 2.550 | **-0.148** | 27.59% |
| byte0 | 0.24 | 2.543 | **-0.149** | 28.03% |

결합 엔트로피 8.416비트 중 **5.09비트가 byte0/byte1에 몰려 있는데 둘 다 누설이
가장 약하다.** 즉 멀티태스크의 이득은 "약한 바이트를 학습할 수 있는가"에 전적으로
달려 있다. 선형 프로브로는 실패했고, 강한 CNN이 해내는지는 미검증이다.

**헤드별 PI_h를 반드시 확인할 것.** 어떤 헤드의 PI_h가 음수면 그 헤드는 정보를
주는 게 아니라 뺏고 있으므로 `loss_weights`에서 낮추거나 뺀다.
`v3_benchmark.multitask_table()`이 이 분해를 자동으로 출력한다.

### 10.4 효율 지표: PI (Perceived Information)

학습 방식마다 라벨이 다르면 정확도끼리 비교가 불가능하다. 그래서 중심 지표를
**PI**로 잡는다.

```
PI = H(Y) - E[-log2 p_model(y|trace)]        [비트/트레이스]
필요 트레이스 ~= log2(q) / PI = 23.0 / PI
```

**이 예측이 실측과 맞는지 검증했다.**

```
PI 2.251비트 -> 예측 10.2 트레이스
실측 SR100% 도달: 10 트레이스        (예측/실측 = 1.02)
```

정확도만으로는 안 되는 이유도 같이 확인된다. 아래는 같은 라벨(HW)에서
모델 품질만 바꾼 것이다.

| 모델 | Top-1 | PI | H 대비 | 예측 트레이스 |
|---|---|---|---|---|
| 매우 좋음 | 76.77% | 3.145 | 74.6% | 7.3 |
| v2 수준 | 47.45% | 2.254 | 53.5% | 10.2 |
| 약함 | 25.91% | 1.309 | 31.1% | 17.6 |
| 학습 실패 | 0.80% | **-0.823** | -19.5% | 무한 |

PI가 **음수**가 될 수 있다는 점이 중요하다. 모델이 확신을 갖고 틀리면 정보를
주는 게 아니라 오히려 **뺏는다.** 정확도로는 이 상태를 구분할 수 없다.

`v3_benchmark.py`가 이 지표들과 비교표 생성을 담당한다.

### 10.5 앙상블 (`v3_ensemble.py`)

SCA에서 앙상블은 문헌의 정설이지만, **어떤 다양성을 쓰느냐가 결정적**이다.
선형 프로브로 네 가지 구성을 실측했다.

| 구성 | 오차 상관 | 앙상블 이득 | 앙상블 PI |
|---|---|---|---|
| 배깅 (같은 창, 데이터 재추출) | 0.946 | 1.003배 | 0.954 |
| 중첩 창 (폭만 확대) | 0.432 | 1.018배 | 1.081 |
| disjoint 창 | 0.258 | **1.195배** | 0.784 |
| **넓은 창 + disjoint (권장)** | - | 1.108배 | **1.177** |

**중첩 창은 앙상블 멤버로 부적합하다.** 오차 상관 0.432로 다양성이 있어 보이지만
넓은 창이 좁은 창을 완전히 포함하므로 우열 관계이고, 학습된 가중치가 가장 넓은
멤버에 0.93으로 몰려 사실상 "최고 멤버 고르기"로 퇴화한다. 폭 확대는 앙상블이
아니라 **단일 모델의 기본 설정**으로 쓰는 것이 맞다(PI 0.658 -> 1.060, +61%).

**disjoint 창이 진짜 상호보완을 만든다.** 실측 누설점이 구간별로 나뉜다.

```
[-16,+16] -> -1, +15        [+16,+48] -> +24, +36
[+48,+80] -> +55, +64       [-48,-16] -> (거의 없음)
```

다만 멤버 개개가 약해 절대 PI는 단일 넓은 창보다 낮다.
**넓은 창 1개(주력) + disjoint 보조 멤버들**이 실측상 최선이었다
(`recommended_specs()`).

결합 방식은 셋 중 캘리브레이션셋 PI가 가장 높은 것을 고른다
(`select_combine_mode()`). 가중치는 EM으로 학습하며 scipy가 필요 없다.
**공격셋으로 고르면 v2가 온도를 공격셋에서 고른 것과 같은 오류**가 된다.

**중요한 한계**: 선형 모델은 분산이 매우 작아 위 수치가 **신경망 앙상블을
과소평가한다.** 신경망은 초기화와 SGD 잡음 때문에 분산이 크고, 문헌에서도 시드
앙상블 이득이 크게 보고된다. 배깅 1.003배를 "시드 앙상블 무용"으로 읽지 말 것.
실기에서 PI로 직접 확인해야 한다.

맥북에서 모델 여러 개를 따로 학습하기 부담스러우면
`make_snapshot_callback()`으로 한 번의 학습에서 스냅샷 앙상블을 얻을 수 있다
(cyclic LR, 비용 1/N).

### 10.6 Ranking Loss (`v3_ranking.py`) — 구현했으나 실측 결과 비권장

Zaid et al.(CHES 2021)의 SCA 전용 손실. 교차 엔트로피가 "HW 맞히기"를
최적화하는 반면 RkL은 **정답 키가 1등이 되기**를 직접 최적화한다.

```
s(m) = sum_i log p( HW(MR(c_i * cand_m)) | trace_i )
RkL  = sum_{m != m*} log2( 1 + exp( -alpha * (s(m*) - s(m)) ) )
```

**데이터셋 제약과 해결**: 원 논문은 (평문, 키) 쌍이 필요하다. 우리 대응물은
(c, s)인데 **DSCAD 프로파일링에는 c도 s도 없다**(attack 쪽에만 있다).
u로부터 일관된 쌍을 역산해 해결했다. 가짜키 s*를 고정하면

```
c_i = u_i * 2^32 * (s*)^-1  (mod q)      ->  MR(c_i * s*) = u_i
```

실측 검증: 잔여류 일치 100%, 정수까지 일치 99.83~100%.
모델은 c를 보지 않고 트레이스만 보며 라벨 u는 실제 측정값이므로 타당한 구성이다.

**구현 검증**: 해석적 기울기 vs 유한차분 최대 오차 **2.68e-08**.
가설표의 정답 후보 HW가 실제 라벨과 정확히 일치함도 확인했다.

**그런데 실측 결과는 부정적이다.**

| 손실 | Top-1 | PI(보정 전) | 학습된 T | PI(보정 후) |
|---|---|---|---|---|
| **CE 단독** | 20.39% | **0.691** | 1.20 | **0.710** |
| CE + RkL | 14.89% | -10.143 | 8.80 | 0.215 |
| RkL 위주(ce=0.2) | 15.10% | -20.119 | 10.00(상한) | -0.219 |

**PI가 -10 ~ -20으로 붕괴한다.** 확신을 갖고 틀리는 상태다. 온도 보정을 해도
CE의 1/3까지밖에 회복되지 않는다.

원인은 손실의 구조다. RkL은 누적 점수의 **상대적 순서만** 제약하므로 로그확률
전체를 상수배해도 값이 거의 변하지 않는다. **절대 확률 크기를 붙잡는 항이 없다.**
선형 모델의 한계가 아니라 손실 자체의 성질이므로 신경망에서도 같은 방향일 가능성이
높다. 우리 공격은 로그확률을 누적하므로 캘리브레이션이 곧 성능이다.

부수 효과로 `fit_temperature`의 온도 그리드 상한을 10에서 30으로 넓혔다.
과신이 심한 모델이 경계에 닿아 보정이 덜 된 채 통과하고 있었다.

**결론**: CE를 기본으로 쓴다. RkL은 실험용으로 남기되 `ce_weight >= 1.0`,
학습 후 온도 보정 필수, PI가 CE 단독보다 낮으면 채택하지 않는다.

### 10.7 시도해볼 학습 방식 목록

우선순위 순이다. 앞의 두 개는 실측 근거가 있고, 뒤로 갈수록 추정이다.

| 방식 | 근거 | 기대 |
|---|---|---|
| window 96~128 + offset 24~32 | 실측 +9.7~12.4% | 확실 |
| 멀티태스크 (sign+byte0~2) | 엔트로피 2.10배 | 큼, 검증 필요 |
| 앙상블 (모델 3~5개 평균) | SCA 문헌 정설 | 중간, 확실 |
| label smoothing 조정 | 캘리브레이션 개선 | 작음 |
| 더 큰 모델 (3천만 샘플이 받쳐줌) | 데이터 충분 | 중간 |
| 순서형(ordinal) 소프트 라벨 | HW가 순서형 | 작음~중간 |
| ~~ranking loss~~ | 실측 PI 붕괴 | **비권장** (10.6 참조) |

**하지 말 것**: `class_weight`(확률 왜곡), 강한 `shift_aug`(실측 순손실),
focal loss와 class_weight 동시 사용, 중첩 창을 앙상블 멤버로 사용,
ranking loss를 낮은 `ce_weight`로 단독 사용.

## 11. 메모리 지침

트레이스는 int64로 저장되어 있어 set 하나가 3.05 GB다. ADC 데이터에 int64는
4배 낭비이므로 로드 즉시 float32로 캐스팅한다. `iter_profiling_traces()`가
청크 스트리밍을 담당하며, **원본을 통째로 메모리에 올리지 않는다.**
POI 슬라이스만 유지하면 40,000 x n_poi x 4 B로 축소된다.
