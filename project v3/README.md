## 1. 이 프로젝트가 무엇을 하는가

### 1.1 전자서명과 비밀키

인터넷에서 "이 문서는 진짜 내가 보낸 것"임을 증명하는 기술이 **전자서명**이다.
서명하는 사람만 아는 값을 **비밀키(secret key)**, 누구나 볼 수 있어서 서명이
진짜인지 검증하는 데 쓰는 값을 **공개키(public key)** 라고 한다.

비밀키가 새어나가면 아무나 그 사람인 척 서명할 수 있다. 그래서 비밀키는
절대 밖으로 나오면 안 된다.

### 1.2 Dilithium과 포스트양자 암호

지금 쓰는 전자서명(RSA, ECDSA 등)은 충분히 큰 양자컴퓨터가 나오면 깨진다는 것이
수학적으로 알려져 있다. 그래서 미국 표준기관 NIST가 "양자컴퓨터로도 못 깨는"
새 알고리즘을 공모했고, 전자서명 부문에서 **CRYSTALS-Dilithium**이 표준으로
선정됐다. 이런 알고리즘들을 **포스트양자 암호(PQC, Post-Quantum Cryptography)** 라
부른다.

Dilithium은 수학적으로는 안전하다. 이 프로젝트는 **수학이 아니라 그것을 돌리는
물리적 칩**을 공격한다.

### 1.3 부채널 공격이란

금고를 부수지 않고, 금고가 내는 소리나 열을 관찰해서 안의 내용을 추측하는 것과
같다. 칩이 계산을 할 때 **전기를 얼마나 쓰는지**는 바깥에서 잴 수 있다.
0을 다룰 때와 1을 다룰 때 소비 전력이 미세하게 다르기 때문에, 전력 파형을 잘
분석하면 칩 안에서 어떤 값을 계산 중인지 알아낼 수 있다.

이렇게 알고리즘 자체가 아니라 구현체가 흘리는 물리적 정보(전력, 시간, 전자파,
소리)를 이용하는 공격을 **부채널 공격(Side-Channel Attack, SCA)** 이라 한다.

이 프로젝트에서 재는 물리량은 **전력**이고, 시간에 따른 전력 사용량을 기록한
데이터 한 줄을 **전력 트레이스(power trace)**, 줄여서 트레이스라고 부른다.

### 1.4 프로파일링 공격

부채널 공격에는 두 종류가 있다.

- **비프로파일링 공격**: 공격 대상 장비의 트레이스만 가지고 통계적으로 추측한다.
- **프로파일링 공격**: 공격자가 **똑같은 모델의 장비를 하나 미리 확보**해서,
  비밀키를 자기 마음대로 바꿔가며 "이 값을 계산할 땐 전력 파형이 이렇게 생겼다"를
  대량으로 학습해둔다. 그 다음 진짜 공격 대상에 적용한다.

프로파일링 공격이 훨씬 강력하고, 이 프로젝트가 하는 것이 그것이다.
학습에 쓰는 데이터를 **프로파일링 데이터**, 실제로 키를 알아내려는 대상의 데이터를
**공격(attack) 데이터**라고 부른다.

딥러닝이 들어오는 지점이 여기다. "전력 파형 → 계산 중인 값"을 학습하는 것은
"사진 → 고양이/개"를 학습하는 것과 구조가 같은 분류 문제다.

## 2. 정확히 어느 지점을 공격하는가

### 2.1 노리는 연산

Dilithium이 서명을 만드는 중에 이런 계산을 한다.

```
u = c · s  (mod q)
```

- `s`: **비밀키**. 우리가 알아내려는 값.
- `c`: **challenge**. 서명에 같이 들어가서 **누구나 볼 수 있는 공개 값**.
- `q`: 8,380,417. Dilithium이 쓰는 소수. 모든 계산이 이 수로 나눈 나머지로 이뤄진다.
- `u`: 중간 계산 결과. 밖으로 나오지 않지만, **계산되는 순간 전력을 소비한다.**

공격 논리는 이렇다.

1. 전력 파형에서 `u`가 무엇이었는지 딥러닝으로 추정한다.
2. `c`는 공개되어 있으니 이미 안다.
3. `u ≈ c · s` 이므로, `c`를 알고 `u`를 추정하면 **`s`를 역산할 수 있다.**

### 2.2 "계수"가 무엇인가

`s`와 `c`는 하나의 숫자가 아니라 **다항식(polynomial)** 이다. 다항식은 쉽게 말해
**숫자 여러 개를 한 줄로 늘어놓은 것**이다. Dilithium에서는 한 다항식이 숫자
**256개**로 이루어지고, 그 숫자 하나하나를 **계수(coefficient)** 라고 부른다.

그리고 비밀키 `s`는 이런 다항식이 **4개** 있다. 그래서 비밀키 전체는

```
4개 다항식 × 256개 계수 = 1024개의 숫자
```

이다. 키를 완전히 복구한다는 것은 이 1024개를 전부 알아낸다는 뜻이다.

### 2.3 곱셈이 계수별로 따로 일어난다

보통 다항식 곱셈은 모든 계수가 서로 뒤섞이는 복잡한 연산이다. 그런데 Dilithium은
**NTT(수론적 변환, Number Theoretic Transform)** 라는 형태로 값을 바꿔놓고 계산한다.
NTT를 거치면 다항식 곱셈이 **같은 위치끼리의 단순 곱셈**으로 바뀐다.
이것을 **pointwise(계수별) 곱셈**이라고 한다.

데이터셋 제작자가 제공한 공식 검증 노트북이 이 관계를 정확히 정의하고 있고,
우리도 직접 재검증했다.

```
u[i][j][k] = MR( c[i][k] × s[j][k] )

  i : 몇 번째 서명인가        (0 ~ 9999)
  j : 몇 번째 다항식인가      (0 ~ 3)
  k : 몇 번째 계수인가        (0 ~ 255)
```

**이것이 이 공격을 가능하게 하는 핵심이다.** 계수 하나하나가 독립적으로 곱해지므로,
1024개 숫자를 하나씩 따로 공략할 수 있다. 1024개를 동시에 맞힐 필요가 없다.

### 2.4 MR(Montgomery Reduction)이 무엇인가

`c × s`를 계산하면 `q`(838만)보다 훨씬 큰 수가 나온다. 이걸 다시 `q`로 나눈
나머지로 되돌려야 하는데, 나눗셈은 칩에서 매우 느리다.

**몽고메리 리덕션(Montgomery Reduction, MR)** 은 나눗셈 없이 곱셈과 비트 시프트만으로
나머지 연산을 해내는 기법이다. 실제 구현은 이렇게 생겼다.

```python
def MR(d):
    g = int32(d * qinv)      # qinv는 미리 계산해둔 상수
    return (d - g * q) >> 32  # 32비트 오른쪽 시프트
```

우리가 노리는 것은 이 MR의 **출력값 `u`** 다. 이 값이 32비트 레지스터에 올라가는
순간 전력이 소비되고, 그 전력이 값에 따라 달라진다.

참고로 `d * qinv`는 64비트를 넘쳐서(overflow) 잘려나가는데, **그 잘림이 알고리즘의
일부**다. 원본 노트북에서 오버플로 경고가 뜨는 이유가 이것이고, `v3_common.mr()`은
이 동작을 numpy에서 정확히 재현한다.

### 2.5 왜 값 자체가 아니라 "해밍 웨이트"를 맞히는가

`u`가 가질 수 있는 값은 838만 가지다. 838만 개 중 하나를 고르는 분류 문제는
딥러닝으로 학습이 불가능하다.

다행히 물리적으로 새어나오는 정보는 값 자체가 아니다. 칩의 전력 소비는 대체로
**레지스터에 1이 몇 개 켜져 있는지**에 비례한다. 이진수로 바꿨을 때 1의 개수를
**해밍 웨이트(Hamming Weight, HW)** 라고 한다.

```
u = 5  →  이진수 101  →  HW = 2
u = 7  →  이진수 111  →  HW = 3
```

32비트 레지스터라면 HW는 0부터 32까지, 즉 **33가지**다. 838만 대신 33가지를
맞히는 문제가 되므로 학습이 가능해진다. 이것이 33개 클래스 분류인 이유다.

### 2.6 라벨 분포가 봉우리 두 개인 이유 (중요)

코드는 해밍 웨이트를 이렇게 계산한다.

```python
bin(u & 0xFFFFFFFF).count('1')
```

`& 0xFFFFFFFF`는 "32비트로 잘라서 본다"는 뜻이다. 여기서 중요한 일이 벌어진다.

- `u`가 **양수**면 (예: 4,000,000) 이진수로 23비트쯤이고 1이 **11~12개** 정도다.
- `u`가 **음수**면 컴퓨터는 2의 보수 방식으로 표현하므로 위쪽 비트가 대부분 1이
  된다. 그래서 1이 **20~22개**로 확 늘어난다.

실측한 공격 데이터에서 음수 5,035개 / 양수 4,965개로 거의 반반이다. 그 결과
HW 분포가 **봉우리 두 개짜리(이봉분포)** 가 된다.

```
HW=11 근처 (양수 무리)  8.68%  <- 가장 흔함
HW=21 근처 (음수 무리)  8.28%
```

**이것이 성능 평가에 결정적이다.** 무작위로 찍으면 1/33 = 3.03%지만,
**"무조건 HW=11"이라고만 답해도 8.68%가 나온다.** 그러므로 모델 정확도는
3.03%가 아니라 **8.68%와 비교해야 의미가 있다.** v3 코드는 정확도를 출력할 때
항상 이 값을 같이 찍는다.

## 3. 데이터셋이 어떻게 생겼는가

전체 15.3 GB다.

| 파일 | 모양 | 뜻 |
|---|---|---|
| `profiling_40000traces_set1~4.npy` | (10000, 40000) | 학습용 트레이스. 4개 파일 합쳐 40,000개 |
| `profiling_40000_u=cs.npy` | (40000, 4, 256) | 학습용 정답 `u`. 트레이스마다 1024개 |
| `attack_10000traces.npy` | (10000, 40000) | 공격 대상 트레이스 10,000개 |
| `attack_10000_u=cs.npy` | (10000, 4, 256) | 공격셋의 `u` (검증용) |
| `attack_10000_c.npy` | (10000, 256) | 공개 challenge 값 |
| `attack_s.npy` | (4, 256) | **진짜 비밀키.** 채점용으로만 씀 |
| `rho.npy` | (20, 40000) | 미리 계산된 상관계수 분석 결과 |

### 3.1 "(10000, 40000)"이 무슨 뜻인가

**10,000개의 트레이스가 있고, 트레이스 하나는 40,000개의 숫자로 이루어져 있다.**

40,000개의 숫자는 시간 순서대로 찍은 전력 측정값이다. 오실로스코프로 서명 연산
한 번을 녹화하면서 아주 짧은 간격으로 4만 번 전압을 기록했다고 보면 된다.
이 4만 개 각각을 **시간 샘플(time sample)** 이라고 부른다.

실측해보니 트레이스 하나에 **서로 다른 값이 109개뿐**이다. 측정 장비의 해상도가
그만큼 성기다는 뜻이다. 그래서 이 데이터를 int64(8바이트)로 저장한 것은 심한 낭비이고,
float16(2바이트)으로 바꿔도 정보가 전혀 손실되지 않는다. v3가 이 변환을 한다.

### 3.2 결정적인 사실: 한 트레이스 안에 1024개가 다 들어있다

`u`의 모양이 `(40000, 4, 256)`이라는 것은, **트레이스 i 하나에 대해 정답이
4 × 256 = 1024개** 있다는 뜻이다.

왜 그럴까? 서명 연산 한 번이 1024개 계수를 **순서대로 전부 계산**하기 때문이다.
40,000개 시간 샘플 안에 1024개의 곱셈이 차례로 들어있는 것이다.
계수 하나당 대략 30~35개 시간 샘플을 차지한다.

**v2는 이 1024개 중 딱 하나(`u[:, 0, 50]`)만 사용했다.** 사진 한 장에 1024명이
찍혀 있는데 한 명만 보고 있었던 셈이다. v3의 가장 큰 변화가 이것을 전부 쓰는 것이다.

### 3.3 rho.npy의 정체 (해독함)

`rho.npy`는 (20, 40000)인데 20이 무엇인지 문서에 없었다. 각 행의 최대값 위치를
찾아보니 규칙이 드러났다.

```
poly0: 1828  3578  5328  7078  8828
poly1: 11831 13388 14888 16388 17888
poly2: 21578 23078 24578 26078 27578
poly3: 31578 33078 34578 36078 37578
```

**20 = 4개 다항식 × 5개 계수**였다. 다항식 구간이 정확히 10,000 샘플
(= 40,000 ÷ 4) 간격으로 배치되어 있다.

여기서 "상관계수(rho)"란 두 값이 얼마나 함께 움직이는지를 -1~1로 나타낸 수치다.
0이면 무관, 1에 가까우면 완벽히 같이 움직인다는 뜻이다. 여기서는
**"이 시간 샘플의 전력값"과 "그 순간 계산되는 값의 해밍 웨이트"** 사이의 상관계수다.

최대값이 **0.7249**다. 부채널 공격에서 이 정도면 누설이 대단히 강한 편이다.
그리고 그 지점을 조금만 벗어나면 0.022로 떨어진다. 즉 **누설이 극도로 국소적**이다.

## 4. v2가 무엇을 했고, 무엇이 문제였나

v2는 실제로 작동하는 공격을 만들었다. 단일 트레이스 정확도 54.35%는 다수 클래스
베이스라인 8.68%의 **6.3배**로, 진짜 신호를 학습한 것이 맞다. 이 점은 분명히 해둔다.

문제는 다른 곳에 있었다.

### 4.1 성적표가 조작되어 있었다 (가장 심각)

키 복구 성능을 재는 코드가 이렇게 생겼다.

```python
s_candidates = np.unique(s_atk_all[0])   # attack_s.npy = 정답 비밀키 파일
```

**후보 답안지를 정답 파일에서 만들었다.** 객관식으로 비유하면, 원래 838만 개
보기 중에 골라야 하는 문제인데, 정답이 반드시 포함된 256개짜리 보기를 정답지에서
뽑아다 쓴 것이다. 실제 공격자는 `attack_s.npy`를 절대 볼 수 없다.

축소 배율을 계산하면 **8,380,417 ÷ 256 = 32,736배**다.

### 4.2 동점자를 세지 않았다

순위를 이렇게 계산했다.

```python
rank = np.sum(s_log_probs > s_log_probs[correct_s_idx])
```

"나보다 점수가 **높은** 후보가 몇 명인가"만 센다. 동점자는 0명으로 친다.

그런데 해밍 웨이트는 33가지뿐이라, **서로 다른 비밀키 후보가 완전히 똑같은 HW
관측 결과를 내는 일이 매우 흔하다.** 특히 트레이스가 적을 때 그렇다.
실제로 완벽한 오라클(HW를 100% 맞히는 가상의 이상적 모델)로 실험해보면,
동점을 안 세면 트레이스 1개만 봐도 "순위 0등, 복구 성공"이 나온다.
정상적으로 동점을 반영하면 순위 **2,116등**이다.

즉 아직 아무것도 좁히지 못했는데 성공한 것처럼 보이는 상태였다.

### 4.3 온도 조절이 반대 방향이었다

모델이 내놓는 답은 "HW=11일 확률 40%, HW=12일 확률 25%..." 같은 **확률 분포**다.
여러 트레이스의 확률을 곱해 나가며 후보를 좁히는 것이 공격의 원리다.

이때 모델이 지나치게 자신만만하거나 지나치게 소심하면 결과가 왜곡된다. 그래서
확률을 전체적으로 날카롭게/뭉툭하게 조절하는 **온도 스케일링(temperature scaling)**
이라는 보정을 한다. `T`가 1보다 크면 뭉툭해지고, 1보다 작으면 날카로워진다.

v2는 `T = 5.0`, 즉 **뭉툭하게** 만들었다. 그리고 그 값을 공격셋에서 직접 골랐다
(시험 문제를 보고 공부법을 정한 셈이다).

정확도를 제어한 합성 모델로 제대로 실험해보니 학습되는 최적 온도는 **약 0.4**,
즉 **날카롭게** 만드는 방향이었다. v2는 스스로 눈을 흐리게 하고 "잘 안 보이니
사진을 50장 찍자"고 한 상태였다. 제대로 하면 10장 미만으로 충분하다.

### 4.4 POI가 250개가 아니라 4개였다

**POI(Point of Interest)** 는 "트레이스 4만 개 샘플 중 실제로 정보가 새는 지점"이다.
전부 쓰면 계산이 무겁고 잡음만 늘어나므로 알짜만 골라낸다.

v2 보고서는 "시맨틱 피크 250개"를 골랐다고 적었다. 실제 코드는 이렇다.

```python
peaks, properties = find_peaks(target_rho, height=0.03, distance=30)
top_peak_indices = peaks[np.argsort(properties['peak_heights'])[-250:]]
```

`[-250:]`는 "뒤에서 250개"라는 뜻인데, **원소가 4개뿐이면 조용히 4개만 준다.**
에러도 경고도 없다. 저장된 파일을 열어보면 `poi_indices.npy`는 60개
(= 4개 피크 × 15샘플 윈도우)이고, 파일 이름이 `X_train_poi400.npy`인데 실제
모양은 `(40000, 60)`이다.

여기에 이동평균 필터가 인접 샘플을 뭉개므로, 15샘플 윈도우 안의 실질적인 독립
정보는 3개 정도다. **모델이 실제로 본 정보는 약 12개 숫자**였던 셈이다.

### 4.5 손실 함수가 확률을 망가뜨렸다

v2는 두 가지 불균형 보정을 **동시에** 걸었다.

- `CategoricalFocalCrossentropy`: 흔한 클래스의 영향력을 줄이는 손실 함수
- `class_weight='balanced'`: 희귀 클래스에 가중치를 더 주는 옵션

둘 다 "희귀한 것을 더 챙겨라"는 같은 목적이라 **이중으로 걸린다.** 그 결과 모델이
내놓는 확률이 실제 확률에서 크게 벗어난다. 앞서 말했듯 이 공격은 확률을 곱해
나가는 방식이라 **확률이 정확해야 한다.** T=5.0이라는 땜질이 필요했던 근본 원인이 이것이다.

덧붙여 focal loss의 `alpha=0.25`는 다중 클래스에서 모든 클래스에 똑같이 곱해지므로
실질적으로 **학습률만 0.25배로 줄이는** 효과밖에 없다.

### 4.6 "검증 정확도 > 학습 정확도"를 잘못 해석했다

v2 보고서는 검증 정확도가 학습 정확도보다 높은 것을 "모델이 암기가 아니라 물리적
본질을 학습한 증거"라고 적었다.

실제로는 `Dropout(0.6)` 때문이다. 드롭아웃은 학습 중에 뉴런의 60%를 무작위로
꺼버리는 기법인데, **학습 정확도는 이 방해가 켜진 채로, 검증 정확도는 방해 없이**
측정된다. 강한 드롭아웃이면 항상 나타나는 현상이지 일반화의 증거가 아니다.

### 4.7 모델이 붙어있지 않은 조각들을 이어붙여 봤다

v2의 입력 60개 샘플은 **물리적으로 멀리 떨어진 4개 구간을 이어붙인 것**이다.
그런데 모델은 이것을 하나의 연속된 신호로 보고 폭 11짜리 필터를 훑는다.
15샘플마다 있는 인위적 경계를 필터가 가로지르며 **무관한 시간대를 섞는다.**
게다가 풀링을 3번 거쳐 60 → 7로 줄인 뒤 평균을 내버려서 구간 구분이 완전히 사라진다.

### 4.8 문서와 실제가 다른 부분들

- v1/v2 문서: "총 160,000개 트레이스" → **실제 40,000개** (set 하나가 10,000개)
- v2 보고서: "Log-Prior Correction 적용" → **코드에 존재하지 않음**
- v2 보고서: "비밀키 완벽 복구" → **1024개 중 계수 1개 복구**

## 5. v3가 어떻게 고쳤는가

### 5.1 정규화 — 왜 필요하고 무엇을 하는가

**정규화(normalization)** 는 데이터를 비교 가능한 기준으로 맞추는 작업이다.
왜 필요한지부터 보자.

전력을 재는 장비의 컨디션은 날마다 다르다. 어제는 전체적으로 조금 높게, 오늘은
조금 낮게 잰다. 모델이 "전력이 높으면 HW가 크다"를 배웠는데 장비 때문에 전체가
밀려버리면 배운 것이 무용지물이 된다. 정규화는 **키를 재기 전에 신발을 벗기는 일**이다.

정규화에는 방향이 두 가지 있다.

- **수직(vertical) 정규화**: "시간 샘플 1828번의 값"을 여러 트레이스에 걸쳐 모아서
  평균 0, 표준편차 1로 맞춘다. 시간 위치별로 기준을 잡는 방식이다.
- **수평(horizontal, per-trace) 정규화**: 트레이스 하나 안에서 4만 개 값을 모아
  그 트레이스만의 기준으로 맞춘다. 트레이스별 개인차를 없애는 방식이다.

v2 문서는 "개별 트레이스 정규화 금지"를 강하게 못박았다. 그 경고는 **POI 구간
안에서만 수평 정규화를 할 때** 맞는 말이다. 그 좁은 구간에서는 신호 자체가
분산의 대부분이라, 정규화하면 신호를 지워버린다.

하지만 **트레이스 전체 4만 샘플**에서 재면 이야기가 다르다. 데이터에 의존하는
성분은 전체 분산의 아주 일부이므로, 신호를 지우지 않고 장비 이득만 제거할 수 있다.
v3는 이 순서로 처리한다.

```
이동평균 필터 → 트레이스별 이득 보정 → POI 추출 → 시간 샘플별 수직 정규화
```

또 하나 바꾼 것은 **수직 정규화에 쓸 통계를 어디서 가져오는가**다. v2는 프로파일링
데이터의 평균/표준편차를 공격 데이터에 그대로 적용했다. 그러면 두 측정 세션 사이의
차이가 그대로 남는다. 공격자는 공격 트레이스 1만 개를 손에 쥐고 있으므로
**그 데이터 자신의 평균/표준편차를 계산하는 것은 정답을 전혀 쓰지 않는 정당한
작업**이다. `vertical_source="own"`이 기본값이고, `"external"`로 두면 v2 동작을
재현해 비교할 수 있다.

**실측으로 정정된 부분이 두 가지 있다.** 정직하게 적어둔다.

첫째, **이동평균 필터는 확실히 도움이 된다.** 이동평균이란 인접한 몇 개 샘플을
평균 내어 부드럽게 만드는 것으로, 고주파 잡음을 줄인다. 처음에는 "필터가 정보를
뭉갤 수 있으니 빼고 비교해보라"고 권고했는데, 실제 트레이스 600개로 재보니 틀렸다.

```
필터 없음  0.6653      폭 3   0.7312      폭 5   0.7434
폭 7  0.7589 (최적)    폭 9   0.7442      폭 11  0.7192      폭 15  0.6650
```

폭 7이 정점이다. 기본값을 7로 바꿨다. v2의 5는 최적은 아니었지만 근접했다.

둘째, **트레이스별 이득 보정과 캠페인 자체 통계는 이 데이터셋에서 효과가 없다.**
합성 데이터에 이득 편차를 인위로 주입했을 때는 0.8155 → 0.9356으로 크게
개선됐지만, 그것은 내가 문제를 만들어놓고 푼 것이었다. 실제 데이터로 재보니
차이가 없다.

| 비교 | 결과 |
|---|---|
| 캠페인 내부, 이득 보정 유무 | 0.7427 → 0.7434 |
| 캠페인 간 전이, 이득 보정 유무 | 0.7376 → 0.7385 |
| 캠페인 간 전이, `external` vs `own` | 0.7385 → 0.7386 |

이유는 명확하다. 이 데이터셋의 프로파일링 캠페인과 공격 캠페인이 **매우 잘
정합되어 있어 보정할 편차가 애초에 없다.** 평균 이동이 프로파일링 표준편차의
0.044배(중앙값)에 불과하고 분산 비율은 1.001이다. 프로파일링에서 학습한 모델을
공격셋에 적용했을 때 성능 손실이 **1.4%뿐**이다.

두 옵션은 비용이 없고 해롭지 않으므로 기본값으로 두지만, **이 데이터셋에서
성능 개선을 기대해서는 안 된다.** 측정 세션이 실제로 어긋난 다른 데이터셋을 위한
안전장치로 이해하는 것이 맞다.

**결론적으로 정규화에서 실제 효과가 있었던 것은 이동평균 폭 7 하나다.**
v3의 진짜 기여는 정규화가 아니라 (1) 데이터 1024배 활용, (2) 평가의 정직성 회복,
(3) 시간 매핑 실측이다.

### 5.2 POI 선택 — 조용한 실패를 구조적으로 막는다

v2의 실패는 "조건을 만족하는 게 4개뿐인데 250개를 요청했더니 조용히 4개를 줬다"는
것이었다. v3의 `select_poi()`는 **개수를 보장하고, 확보하지 못하면 예외를 던진다.**
실패가 눈에 띄지 않고 지나갈 수 없다.

지표도 바꿨다. `rho`(상관계수)는 "전력이 HW에 비례해서 직선으로 변한다"는 가정에
묶인다. 대신 **SNR(신호 대 잡음비)** 를 쓴다. SNR은 "HW가 다르면 평균 전력이 얼마나
달라지는가"를 "같은 HW 안에서도 값이 얼마나 흔들리는가"로 나눈 값이라, 관계가
직선이 아니어도 잡아낸다.

### 5.3 학습 — 데이터를 1024배 쓴다 (핵심)

앞서 본 것처럼 트레이스 하나에 계수 1024개가 다 들어있다. 그렇다면 계수마다
따로 모델을 만들 것이 아니라, **모든 계수가 같은 모델을 공유**하게 하면 된다.
이것을 **계수 불변(coefficient-invariant) 모델**이라고 부른다.

원리는 간단하다. 계수 `(j, k)`의 누설이 일어나는 시간 위치를 알아낸 뒤, 그 주변을
잘라내(윈도우) 모델에 넣는다. 어느 계수에서 잘라왔든 모델 입장에서는 똑같이
생긴 입력이다.

이렇게 하면 두 가지가 동시에 해결된다.

- 학습 샘플이 **30,000개 → 30,720,000개(1024배)** 로 늘어난다.
- 모델 하나가 1024개 계수를 전부 담당하므로 **전체 키 복구가 자동으로 따라온다.**
  원래는 별도 단계(Stage 3)로 잡아뒀던 작업이 사라진다.

이게 정말 되는지는 실측으로 확인해야 한다. 두 가지를 쟀다.

**누설 방향이 일치하는가**: 표본 128개 계수 전부에서 상관계수 부호가 음수로
일관됐다. 모든 계수가 같은 방향으로 누설한다.

**섞어도 정보가 유지되는가**: 1024개 계수에서 뽑은 윈도우를 전부 섞었을 때
|rho| = **0.7399**, 계수 하나만 썼을 때 **0.7434**. **거의 손실이 없다.**
가중치 하나로 1024개를 감당할 수 있다는 직접적인 증거다.

모델 구조도 바꿨다. 입력이 **연속된 단일 윈도우**라서, v2처럼 필터가 인위적 경계를
가로지르는 문제가 없다. 손실 함수는 `class_weight`를 빼고 표준 교차 엔트로피에
label smoothing만 쓴다. 확률 보정은 학습이 끝난 뒤 온도로 따로 처리한다.

증강(augmentation, 데이터를 살짝 변형해 늘리는 기법)도 바꿨다. v2의
`GaussianNoise(0.05)`는 이미 표준편차 1로 정규화된 데이터에 0.05짜리 잡음을 더하는
것이라 사실상 아무 효과가 없다. v3는 **윈도우 중심을 몇 샘플 흔드는 방식**을 쓴다.
정렬 오차에 대한 강건성을 직접 학습시키는, 물리적으로 의미 있는 증강이다.

다만 실측 결과 이것도 공짜가 아니다.

```
흔들기 0칸  0.7399     1칸  0.7236     3칸  0.6647     5칸  0.5656
```

시간 위치를 계수별로 정확히 측정해뒀으므로 정렬이 이미 좋다. 큰 증강은 순손실이며
**1~2칸을 권장**한다.

검증 방식도 바꿨다. 무작위로 나누면 같은 측정 세션 안에서 나누는 것이라 성능이
낙관적으로 나온다. v3는 **set 하나를 통째로 검증용으로 빼는(leave-one-set-out)**
방식을 쓴다.

### 5.4 평가 — 정직한 성적표

**후보 공간을 정답에서 만들지 않는다.** `build_candidate_residues()`는 시드를
고정한 난수로 `[0, q)` 범위에서 후보를 뽑는다. 정답 키 파일은 후보 생성에
전혀 쓰이지 않는다. 정답은 오직 "몇 등인지 매길 대상"으로만 삽입된다.

여기서 확인해야 할 수학적 문제가 하나 있었다. 실제 `attack_s.npy`의 값은
-18,046,164 ~ 19,328,097 범위로 `q`보다 크다. 그렇다면 후보를 `q`개만 열거해도
되는가?

`MR(c × (s + q))`와 `MR(c × s)`가 같은지 실측했고, **같았다.** 수학적으로도
`q × qinv ≡ 1 (mod 2^32)`에서 유도된다. 1024개 계수 × 2,000 트레이스를 전수
검사했더니 불일치는 0.058%뿐이었고, 그 차이도 정확히 ±q인 오버플로 경계 사례였다.
따라서 **후보 공간은 q개가 맞다.**

**동점을 반영한다.** 순위를 "나보다 높은 수 + 동점자 수 ÷ 2"로 계산한다.
이것 하나로 완벽 오라클의 N=1 순위가 0에서 2,116으로 정상화된다.

**보정을 공격셋과 분리한다.** 온도와 사전확률 보정은 별도의 캘리브레이션셋에서만
학습한다. 시험지를 보고 공부법을 정하는 일이 구조적으로 불가능해진다.
`implicit_log_prior()`는 v2 보고서가 주장했지만 구현하지 않았던 사전확률 보정을
실제로 수행한다.

**완벽 오라클 기준선을 항상 같이 보고한다.** HW를 100% 맞히는 가상의 이상적
모델이 몇 개의 트레이스를 필요로 하는지를 재둔 것이다. 어떤 모델도 이보다 잘할 수
없으므로, 성능을 해석하는 절대 기준이 된다.

```
N=1  GE=2116.4  SR=  0.0%
N=2  GE= 132.0  SR=  0.0%
N=3  GE=   7.9  SR=  0.0%
N=4  GE=   0.33 SR= 55.0%
N=5  GE=   0.01 SR= 97.5%
N=6  GE=   0.00 SR=100.0%
```

여기서 **GE(Guessing Entropy)** 는 "정답 키가 평균 몇 등인가"다. 0등이면 1위,
즉 완벽 복구다. **SR(Success Rate)** 은 "몇 %의 실험에서 1위를 차지했는가"다.
`N`은 사용한 트레이스 개수다.

즉 **트레이스 1개가 주는 정보는 약 4비트이고, 후보 공간은 23비트이므로,
어떤 모델도 6개 미만으로는 복구할 수 없다.**

### 6.1 time_map.json이 왜 중요한가

계수 `(j, k)`의 누설이 몇 번째 시간 샘플에서 일어나는지를 담은 표다.
이 값이 틀리면 샘플러가 엉뚱한 구간을 잘라내므로 **학습 자체가 성립하지 않는다.**

처음에는 "다항식마다 일정한 간격으로 배치되어 있을 것"이라 가정하고 직선으로
맞추려 했다. 실제 트레이스로 재보니 틀렸다.

| | 계수 간격 | 직선 적합 오차 |
|---|---|---|
| poly0 | 약 35 (32~37 변동) | 1.1 샘플 |
| poly1 | 앞부분 35 → 뒷부분 30 | **145.7 샘플** |
| poly2 | 약 30 (27~32 변동) | 1.4 샘플 |
| poly3 | 약 30 (27~32 변동) | 1.2 샘플 |

poly1만 도중에 간격이 바뀐다. 직선 하나로는 못 맞춘다. 그래서
**1024개 위치를 전부 개별 측정**해 표로 저장했다.

측정 품질은 **|rho| 중앙값 0.6686, 최소 0.5198, 0.3 미만 0개**다.
1024개 계수 전부가 강하게 누설한다.

### 7.2 순서

```python
import sys; sys.path.insert(0, "project v3")
import v3_common as vc, v3_normalize as nz, v3_stage2_data as s2
import v3_model as vm, v3_evaluate as ev, v3_backend as bk

# 0) 환경 설정 (numpy import 전에 하면 더 좋다)
bk.configure_numpy_threads()
bk.configure_tensorflow()

# 1) 데이터 검증 게이트 — 여기를 통과 못 하면 진행하지 않는다
vc.verify_dataset("../Dataset")

# 2) 정규화된 float16 memmap 생성 (12.2GB -> 3.2GB, 한 번만)
cfg = nz.NormConfig()          # 기본값: MA=7, gain=mad, vertical=own
factory = lambda: vc.iter_profiling_traces("../Dataset")
s2.build_normalized_memmap(factory, "prof_norm.npy", cfg, vc.N_PROFILING)

# 3) 시간 매핑 로드 (실측 테이블)
centers = s2.build_time_map(vc.load_time_map("time_map.json"))

# 4) 샘플러 — 1024개 계수 전부 사용
import numpy as np
X = np.load("prof_norm.npy", mmap_mode="r")
u = vc.load_array("../Dataset", "profiling_40000_u=cs.npy")
hw = s2.precompute_hw_labels(u)
train_idx, val_idx = s2.set_split_indices(val_set=4)

train = s2.CoefficientWindowSampler(X, hw, centers, train_idx,
                                    window=32, batch_size=512,
                                    traces_per_batch=32, shift_aug=1, seed=0)
val   = s2.CoefficientWindowSampler(X, hw, centers, val_idx,
                                    window=32, batch_size=512,
                                    traces_per_batch=32, shift_aug=0, seed=1)

# 5) 학습
model = vm.compile_model(vm.build_model(window=32))
model.fit(s2.to_tf_dataset(train),
          validation_data=s2.to_tf_dataset(val),
          steps_per_epoch=train.steps_per_epoch(),
          validation_steps=200, epochs=50,
          callbacks=vm.make_callbacks())

# 6) 정직한 평가 (공격셋을 캘리브레이션/평가로 분리)
probs = vm.predict_coefficient_probs(model, atk_sampler, atk_idx, poly=0, coeff=50)
T, _  = ev.fit_temperature(probs[cal], hw_true[cal])     # 공격셋 미사용
lp    = ev.implicit_log_prior(probs[cal])
L     = ev.trace_log_likelihood(probs[atk], T, lp)
cands, tidx = ev.build_candidate_residues(65536, seed=42, true_s=true_s)
ge, sr, ge_full = ev.guessing_entropy(L, c_vals, 50, cands, tidx)
ev.summarize(ge, sr, ge_full, label="v3")
```

### 7.3 Apple Silicon에서 알아둘 것

M시리즈 칩은 CPU와 GPU가 **메모리를 공유**한다(통합 메모리). 그래서 데이터를
GPU로 복사하는 비용이 없는 대신, 사본을 늘리면 그만큼 전체 메모리가 줄어든다.
float16 memmap을 쓰는 이유가 이것이다.

성능에 가장 큰 영향을 주는 것은 **배치를 만드는 방식**이다. 3.2 GB 파일에서
무작위 위치를 마구 읽으면 디스크 접근이 흩어져 느려진다. 그래서 샘플러는
**적은 수의 트레이스만 읽고 그 안에서 계수를 많이 뽑는다.** 트레이스 한 줄이
80 KB 연속 읽기가 되어 훨씬 빠르다.

그 밖의 주의사항이다.

| 항목 | 지침 |
|---|---|
| XLA (`jit_compile=True`) | Metal에서 지원 안 됨. 항상 끈다 |
| `mixed_float16` | Metal에서 불안정했던 이력. 기본 off |
| Optimizer | `legacy.Adam`이 M시리즈에서 더 빠른 사례가 있어 우선 시도 |
| Conv1D | `metal_safe=True`면 `(k,1)` Conv2D 경로 사용 |
| float64 | Metal에서 취약. 전 구간 float32 유지 |
| P코어/E코어 | 스레드를 논리코어 전체로 잡으면 효율코어로 밀려 느려진다 |

## 8. 어디까지 검증했는가

이 구분은 중요하다. 코드마다 신뢰 수준이 다르다.

**실제 트레이스로 검증됨**

전체 15.3 GB는 실측 대역폭 약 0.18 MB/s로 24시간이 걸려 받을 수 없었다.
대신 `.npy` 파일이 행 단위로 순서대로 저장된다는 점을 이용해, **HTTP Range 요청으로
앞부분 600행만 잘라 받았다**(183 MB, 8개 병렬 다운로드). 행 `i`의 시작 바이트는
`128 + i × 320000`이다.

- poly0/coeff50의 상관 피크가 **샘플 1828, |rho| = 0.7044** — `rho.npy` 예측과 정확히 일치
- 1024개 계수 위치 전량 실측 (`time_map.json`)
- 이동평균 폭 스윕, 이득 보정 효과, 계수 불변성, 증강 트레이드오프
- **캠페인 간 이식성** — 프로파일링 set1 앞 600행과 라벨 600행을 추가로 확보해 측정.
  시간 매핑이 캠페인 간 그대로 전이되고(위치 차이 중앙값 0샘플),
  전이 손실이 1.4%에 불과하다.
- `v3_common`, `v3_normalize`, `v3_stage2_data`의 numpy 계층 전부

**합성 데이터로만 검증됨**

- `v3_evaluate` — 진짜 `c`/`u`/`s`는 썼지만 모델은 정확도를 제어한 가상 모델이다.
  실제 학습된 모델로 다시 확인해야 한다.

**아직 실행하지 못함**

- `v3_model`, `v3_backend`, `v3_report` — 개발 환경에 TensorFlow가 없어
  **구문 검사와 numpy 부분만 통과**했다. Apple Silicon 실기에서 Metal 인식과
  정밀도를 직접 확인해야 한다.
- 실제 모델 학습과 그에 따른 정직한 GE/SR 측정.
  (프로파일링 트레이스를 600행만 확보해 본격 학습은 불가)
